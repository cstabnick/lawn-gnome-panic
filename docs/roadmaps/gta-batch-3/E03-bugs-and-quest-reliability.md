## Goal
Every quest in the current game can be started, played and finished by a player (and by the quest sim) without a stuck state, and the known visual and world bugs from the list are gone, each with a regression test or a sim check so they stay fixed.

## Scope (what is in, what is explicitly out)
In: the 13 items above, plus extending the quest sim so it proves every existing quest completes (and a sim check for each fix where practical). Out: new quests (E20-E22), economy/garage redesign (E08 owns the multi-car garage and insurance; L09 here only *uses* the existing Lock-Up `callDelivery`), collision model changes (E02 owns `collide.ts`; E03 fixes placements, i.e. which boxes exist and where), map/UI (E07). Quest text rewrites belong to E04/E20; if a fix needs a new line of dialogue keep it minimal.

## Code pointers (confirmed)
Paths under `games/gnome-theft-auto/src/` unless noted.

**L03 follow quests.** Objective runner `quests/objectivesDrive.ts` `chaseFollowRun` (~252-380): the leader is steered by `steerToward` with no road pathing (`expandRoadWaypoints`), halts completely while the player is further than `maxDist * 1.05` with only a "Wait up!" line (no timeout, no catch-up teleport for the player), `stuckT` triggers a 3 m nudge only when its speed over a frame is `< 0.5 * dt * 10` (about 5 m/s, so a legitimately slow corner `cornerPace = pace * 0.6` can teleport it), and on `leader.exploded || leader.driver !== 'npc'` it respawns at the previous waypoint. Failure modes to test: leader wedged on a box (collision, see E02 round colliders), leader on a canal bridge or the loch shore, player cannot keep up in a slow vehicle (`maxDist`), leader stolen/yanked. Also `escort` style objectives: `objectivesTessieEscort.ts`. Quests using `chase-follow`: grep `kind: 'chase-follow'` in `quests/chapter*.ts`, `cityQuests.ts`, `outskirtsQuests.ts`, `newcomerQuests.ts`, `sideQuests.ts`. Fix plan: a progress watchdog (no progress toward the next waypoint for N seconds => re-path via the road graph (`route.ts`), then teleport-to-road, then give the player a relaxed `maxDist`), a visible "leader is waiting" marker, and a fail-safe skip after a long stall (a prompt to retry from the last waypoint).
Quest sim: `questSim/` (`npm run quest-sim -w games/gnome-theft-auto`, headless; `npm run quest-sim:suites` runs `*.sim.test.ts` with `vitest.sim.config.ts`). `questSim/solvers/drive.ts` `chaseFollowSolver`, `suite.ts`, `coverage.test.ts` (what quests are covered), `plans.ts`, `prereqs.ts`, `checks.ts` (post-conditions), `solvers/drive.sim.test.ts` only exercises `prologue-fresh-kiln` objective 0. Extend: one sim test per quest id in `quests/defs.ts` `QUESTS` (all `chase-follow` objectives at minimum) with a "no stall longer than X seconds" check in `checks.ts`.

**L07 plane frozen, banner moving.** `app.ts` `frame()` returns early while a cutscene is active (~1435-1452) and only calls `liveWorldFrame(dt, live)` (~1372-1403) for live scenes. That function calls `sky.update(dt, cx, ...)`, which moves the NPC aircraft records and the towed banner (`skyTraffic/runtime.ts` ~443 `banner.update`), but the plane meshes are only synced by `for (const veh of vehicles) syncVehicleMesh(veh, dt)` (~1708), which lives after the early return. So the plane body freezes while the banner keeps following the (invisible) simulated position. Fix: in `liveWorldFrame` sync the sky traffic vehicles (`sky.netList()`/vehicle list) each frame, or pass a flag so `sky.update` freezes banners with the planes; for paused (`world: 'paused'`) scenes freeze both. Regression test in `skyTraffic/runtime.test.ts` style: update with `paused` true leaves plane and banner positions unchanged.

**L08 birds frozen.** `birding.update(...)` (`app.ts` ~1951) runs only after the early cutscene return and receives `paused: cutscene.active ...`, so during a live scene bird flocks (`birding/flock.ts`, `birdView.ts`) never step and hang mid-air. Decide: in `liveWorldFrame` step `birding` with `paused:false` but `onFoot:false` (birds keep flying, no popups, no scope) and keep the journal hidden. Critters (`critters.ts`) already update in the live frame.

**L09 vehicle near quest start.** Lock-Up API (`lockup/runtime.ts` `Lockup`): `callDelivery(uid, free)` (Sling-Lift drop, fee and cooldown unless `free`), `instanceOf(uid)`, `list(kind)`; spot choice `lockup/safeSpot.ts` `findSafeSpot`. The player's own vehicle is whatever was last stored/driven. Plan: when a quest starts (`quests/quests.ts` accept path, plus after its intro cutscene returns control) and the player is on foot with no owned vehicle within about 60 m, call `callDelivery(lastDrivenUid, true)` to a safe spot near the start marker, once per quest start; skip for quests that supply their own vehicle (`spawnAt`, race grids, aircraft or boat quests: choose by the first objective kind) and while cutscenes play. Coordinate with E08, which redesigns garage/personal vehicle: use only the public `callDelivery`/`instanceOf` contract and keep the call behind one function `ensureRideNear(x, z)` that E08 can re-point.

**L10 sprinklers.** The "rogue sprinkler geysers" live in `encounters.ts`: `SPRINKLER_SPOTS` at (150,-150), (165,-165), (-25,25), (-42,42) (the last two are in Turfton Park next to spawn), `buildSprinkler` (~115): the jet is a cylinder `CylinderGeometry(0.18, 0.85, 4.4, 12)` at y 2.3, shown for `SPRINKLER_ACTIVE_DURATION = 3.5` s per `SPRINKLER_CYCLE = 9`, launching the player (`SPRINKLER_LAUNCH_VY = 6.5`). That is the "tall water cone". Also check `lawn-sprinkler` prefab uses in `quests/stages/turftonB.ts` (~138) and `packages/prefabs/src/catalog/gnome-theft-auto.ts`. Fix: replace the solid cone with a short arcing droplet effect (pooled particles via `fx.ts`, `fx.waterJet` exists), reduce height to about 1.5 m, remove geysers from the spawn area (first 3 minutes) or give a telegraph (head vibrates, puddle), use the `lawn-sprinkler` prefab for the head (prefab rule), and verify the head is not glitchy (z-fight with grass: `flatLayer`, `docs/rendering.md`; run `npm run zfight`).

**L16 sandpit invisible wall.** Fort Sandpit: `config.ts` `BASE` (from marker `site/fort-sandpit`, `wallHeight`, gate on the north wall), the launch ramp `ramps.ts`/`stunts.ts` list (`airfield-hangar` at (432,-136) is the nearest listed; grep `fort` for the sandpit ramp in the ramp table, `ramps.ts` line ~33 region) and the wall colliders built in `biomes.ts` (search `BASE.wallHeight`). Cause to verify: wall box height `h = wallHeight` is a full-height AABB, and `pushOutOfBoxes` ignores boxes whose top `h <= y` (the vehicle's `v.y`); a vehicle airborne over the ramp has `v.y` below the wall top, so it hits an invisible column that extends above the visible wall or sits above the ramp lip. Fix: make the collider exactly match the visible wall height plus a small margin, and have the ramp's `y` clear it; add a test using `ramps.test.ts`/`collide.test.ts` that launches from the ramp and clears the wall.

**L23 bridges to canal bed.** `waterworks.ts` ~81-90: every bridge uses prefab `arch-road-bridge` placed at `y = b.deck - ARCH_DECK` (6.5) with only `scaleX`/`scaleZ` (`WorkPlacement` has no `scaleY`; apply at ~230). The canal's bridge deck stands only `WATER.bridgeClearance.canal = 2.2` above water (config ~808), with freeboard 1.6 and depth 0.85, so a 6.5 m arch puts piers 4.3 m below the deck, through the canal bed. Fix: scale the arch in Y by `(deck - bedLevel)` or use a low-profile bridge prefab for the canal (add to `packages/prefabs/src/catalog/gta-waterworks.ts`), and add a `waterworks.test.ts` assertion that no bridge prefab base is below the local bed. Check `water.ts` `bridges()` (~567) for `deck`.
